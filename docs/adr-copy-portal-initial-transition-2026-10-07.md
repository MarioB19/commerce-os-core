# Initial portal transition on the recovered copy

The recovered runtime permits four API/web services and requires Ciclo503. The
legacy full installer runs bootstrap and consumers, and the portal used a fixed
legacy network. Installing a fifth container directly would break adoption and
the exact B02 runtime inventory.

Add an explicit `portal-copy` selection for the copy tuple only. It completes the
existing API/web publication first, retains its native `api-web-complete.json`
and task journals, then runs the initial portal transition in the same CI unit.
The client requires completion of both phases; an intermediate API/web success
cannot pass as portal completion. Full remains rejected. Normal later releases
return to `api-web`; repeating this initial transition on v2 is rejected.

The SSH stage lives below a user-owned home. Only its sealed portal input is
promoted into a fresh Root-private directory before either publication phase.
The Root process checks the exact sibling stage/run, regular Root-owned0600
single-link input, bounded stable FD bytes and the digest supplied by CI. The
promoted bytes pass the unchanged complete Root ancestry guard and readback.
Cleanup checks its own directory and exact bytes after both phases; uncertain
custody is preserved and blocks cleanup, without touching the original stage.

The portal phase requires a successful installed API/web receipt, state v1,
frozen policy93, owner lifecycle, immutable65 migrations, bounded private input,
another fresh canonical backup and daily/CI/schedule/maintenance locks. It loads
the same sealed package, uses the existing internal IPv4 proxy, and calls the
existing installer. Before committing the portal's current marker, validate the
five-service inventory, unchanged four core projections/profiles, exact owned
Caddy block replacement, network metadata/memberships, API SHA and portal HTTPS
version. Public contacts are explicitly deferred under Brandon's decision.

The private image seals ten PDF files, including the historical calendar file.
Public version requires nine Core PDFs and `calendar_in_portal=false`. Checking
ten private image hashes does not authorize a calendar download or prove that a
buyer opened any of the nine Core documents.

State v2 binds the portal ID/image/revision, current/runtime/manifest file refs,
new Caddy reference and active proxy digest. CAS changes only preserved_runtime
in the B02 plan, preserving previous plan bytes and static storage/tool/key refs.
Validate the prospective state before plan writes. A partial CAS blocks replay
and automatic rollback. Later API/web releases preserve the portal projection
and refs and check its own portal SHA over HTTPS, independently of the API SHA.

On a known installer failure, use its guarded proxy/current rollback first. Only
an exact own stopped container may be removed by ID, without force or volumes;
verify the original four-service baseline again. Unknown cleanup/proxy state
stays blocked. Retain SQLite bind state, images and releases. Portal preparation
has a separate nested journal/log so the first API/web phase is never overwritten.
Future operations reject a nonterminal nested task too.

This implementation is prepared software. It neither supplies live private
portal input nor changes production selection. B02 transport needs its actual
new plan hash after deployment; schedule stays false. Coverage/custody of newly
created portal configuration and SQLite must be verified separately before
closing recovery. Authentication with both historical code families, protected
downloads and physical WhatsApp delivery/payment/register remain pending.
