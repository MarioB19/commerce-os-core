# Credencial administrativa V5

La vía habitual es una sesión owner vigente y `POST /v1/service-tokens`: scopes y entornos explícitos, allowlist exacta opcional, vigencia máxima 90 días, `Idempotency-Key`, respuesta privada cifrada en idempotencia y token mostrado sólo al destinatario. Los IDs aceptan UUID y perfiles conocidos: `intelligence:openai`, `openai:default`, `openai:assistant`, `creative:searchapi`, `creative:r2`, `creative:elevenlabs`, `provider-budget:global` y referencias válidas `waha:`/`cloud:`. No hay comodines ni ampliación de credenciales existentes.

La alternativa preparada para la solicitud V5 usa administración autenticada existente, sin modificar contraseñas, sesiones, roles o credenciales ajenas. Su autorización fija es el SHA256 del texto completo del usuario: `363c24edb04448cec2f9b041320ae9f24790cb98d1d7d9f3b4d07e4081dbc1cb`. No se ejecuta automáticamente ni durante despliegue.

`scripts/v5-service-token.ts` acepta `inspect`, `issue`, `readback`, `revoke`. Input privado 0600: schema_version 1, operation_id UUID, workspace, hash exacto del email normalizado del propietario existente, authorization_sha256, scopes, allowed_environments, resource_ids, expires_at y motivo. Rechaza owner ausente/inactivo/ambiguo; no crea identidades. Vigencia de este bootstrap: hasta siete días. Su allowlist excluye autorización comercial, activación de warmup, administración de números, campañas y finanzas. `sales:propose` sigue siendo propuesta inerte. `integrations:write` permite también configurar presupuestos por el contrato existente: **omitirlo** cuando sólo se requiere revisar/diagnosticar perfiles existentes.

La credencial sigue siendo principal service/viewer y se vincula al actor owner legítimo para las comprobaciones de membresía vigentes de Inteligencia y del archivo de materiales. Las credenciales nuevas con prefijo cos_v5_ tienen idempotencia separada por token; las credenciales previas conservan su namespace para no duplicar operaciones al repetirlas. Esos scopes sólo habilitan las operaciones concretas concedidas y no permiten emitir tokens, revisar finanzas ni convertirse en sesión owner. Las comprobaciones de gasto/consumo siguen siendo independientes.

El directorio 700 y ledger 600 guardan el secreto antes de INSERT. Auditoría y token se confirman juntos. Un replay con mismo input y ledger recupera el mismo token; input distinto, revocación o pérdida de ledger producen error. Readback compara hash, actor, workspace, scopes, entornos, recursos, plazo y prueba de auditoría. Revoke sólo afecta ese token demostrado por su ledger. No usar `bootstrap.ts` ni cambiar la contraseña para renovar esta credencial.

## Transporte publicado acotado

El job `credential` de `.github/workflows/ci.yml`, mediante workflow_dispatch con `mode=credential`, es manual, sólo `main` del repositorio canónico, SHA esperado igual al HEAD y despliegue actual. Conserva el `workflow_ref` exacto ya permitido por OIDC, sin ampliar IAM. En ese modo se omiten changes/verify/ci-gate/package/deploy; el selector también rechaza credential como release. Reutiliza la cuenta de despliegue e IAP al objetivo existente `vibe-conversa-prod`/`us-east1-d`; no crea cuenta cloud ni llave persistente. Comparte exclusión con despliegue y verifica RELEASE.json, plataforma linux/amd64 y capas ordenadas de la imagen maintenance sellada. Resuelve el digest instalado desde release.env y sólo ejecuta el Id inspeccionado y verificado; containerd puede representar el índice OCI con un Id distinto al del runner, como contempla la verificación de despliegue existente. Ejecuta únicamente el issuer de esa imagen publicada, sin Docker socket montado ni comandos remotos elegidos por input.

El input lleva hash de email y parámetros revisados, nunca contraseña o token. La llave RSA privada (mínimo 3072, preparación actual 4096 bits) permanece en el Mac. El servidor fija el input y destinatario por operation_id, ejecuta y cifra recibo+token con AES256GCM y RSA-OAEP-SHA256 antes de cruzar SSH. El runner exporta exclusivamente ciphertext. Antes de IAP comprueba acceso al repositorio privado; después usa los helpers del transporte privado existente para guardar exactamente `envelope.json` y `envelope.json.sha256` en el draft `v5-credential-<run_id>-<run_attempt>`. El job tiene contents:write sólo para ese escrow; no depende de la cuota de Actions artifacts, no sobrescribe assets y descarga ambos archivos para cotejar sus hashes. El ID y SHA256 del ciphertext quedan en el resumen/log del job. El draft no caduca ni se limpia automáticamente. La llave SSH efímera se retira y caduca a 15 minutos. Un transporte fallido no demuestra emisión fallida: usar `inspect`/`readback` con el mismo input/directorio; no emitir otra identidad silenciosamente.

No copiar estos archivos al vault/Git. El template requiere sustituir expected_sha por el commit main desplegado comprobado. El input actual omite `integrations:write`, todos los scopes de autorización/activación y concede REAL/SIMULATION para preparar configuración y laboratorio; no cambia presupuestos existentes.

Tras dispatch, comprobar main/SHA y éxito del job credential, elegir el draft exacto `v5-credential-<run_id>-<run_attempt>` del repositorio privado, verificar target_commitish y descargar sólo `envelope.json` y `envelope.json.sha256`. La salida imprime sólo estado y ruta. Verificar en receipt.json SHA desplegado, operation_id, owner matched, scopes, plazo y readback antes de instalar service-token en la configuración MCP privada. Conservar la credencial privada mientras el MCP y las operaciones delegadas vigentes la necesiten; revocarla con el mismo workflow e input al terminar ese uso. Su vencimiento no se extiende automáticamente. No imprimir ni adjuntar el token a artifacts, comandos de shell, notas o mensajes.
