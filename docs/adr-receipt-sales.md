# ADR — receipt_sales_v1 (2026-09-06)

Decisión previa a implementación de H1–H6, autorizada por Brandon. El comprobante aprobado es la única fuente de ingreso. No se invoca conciliación bancaria ni se reinterpretan eventos históricos.

- Pedido y comprobante siguen en `records`. `payment_contributions` identifica cada pago: una contribución primaria por pedido; pagos adicionales requieren clave explícita y revisión. Documentos alternativos sustituyen evidencia mediante una decisión explícita, conservando eventos/versiones. Importe positivo en unidades menores y moneda resuelta; nunca usar precio de catálogo como importe cobrado.
- Una función transaccional común reconoce aprobación humana/automática. Usa bloqueo de conversación y evidencia, claves únicas y versión esperada. La proyección SQL excluye Prueba, Falso y documentos sin aprobar en cada consulta; no hace descuentos acumulativos. `sale_id = order_id`.
- Primera aprobación cancela cobros y desbloquea beneficios una vez. Compatibilidad de nodos antiguos `reconcile`: satisfacen el nuevo hecho de pago sin escribir `RECONCILED`. Correcciones/restauración/backfill no ejecutan workflows, entregas, mensajes ni conversiones. Las plantillas nuevas usan aprobación; versiones publicadas se conservan.
- Insights: GET oficial v26.0, cuenta/día/anuncio y control cuenta/día/campaña. Jobs durables con lease/reintento y ventana reciente; reemplazo atómico sólo de rangos completos por cuenta. Errores conservan lectura válida, hora y calidad. Metadata conserva anuncios sin gasto. Permiso de secreto Meta sólo al worker de automatización.
- `conversation_first_observed_v1`: primer touchpoint publicitario observado anterior al pedido. Source ID sólo es anuncio si el proveedor declara tipo ad. Cuenta+ID resuelven jerarquía; ambigüedad queda desconocida. Correcciones manuales requieren motivo y evidencia. No se atribuye por número o nombre.
- Relación campaña/anuncio → producto versionada por fecha. Rendimiento por producto promocionado; ventas por producto vendido. No repartir gasto no clasificado. Reportes agregan en PostgreSQL y paginan detalle, con moneda y zona separadas. Base de impuestos es estimación configurable por cuenta, nunca cargo verificado.
- Histórico ClickChat: preview cifrado, identidad externa estable o hash privado sin posición de fila; colisiones se revisan. Sin archivo = reportada por fuente, fuera de ventas verificadas. Backfill analítico explícito y repetible; no se ejecuta en producción como parte de despliegue.
- API anterior `/reconcile` queda deprecada para consumidores históricos; reportes nuevos usan comprobantes. Exportaciones llevan definición, corte y revisión para detectar reemplazos. El cierre/Personal Tracker legado conserva su contrato externo.
