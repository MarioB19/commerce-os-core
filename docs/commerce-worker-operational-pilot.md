# Piloto Windows conectado a API y R2

El workflow privado `creative-worker-operation.yml` sólo se ejecuta mediante `workflow_dispatch`. Reutiliza un NSIS de un run nativo aprobado: verifica run, SHA de origen, checksum del instalador, Node 24 incluido, firma Ed25519 del runtime y cada archivo instalado. No reconstruye el motor, no descarga entradas del release de comparación y no necesita claves de proveedores.

Antes de disparar, el operador crea un proyecto REAL nuevo dedicado a Oraciones, asigna un único job con `preferred_device_id` y aprueba un dispositivo efímero limitado únicamente a ese proyecto. El proyecto no debe contener otros jobs elegibles. La aprobación humana registra el consentimiento; el runner recibe sólo el pairing ID y su secreto de polling, que caducan en diez minutos y sólo pueden consumirse una vez. El operador configura los secrets privados `COMMERCE_WINDOWS_PAIRING_ID` y `COMMERCE_WINDOWS_POLL_SECRET`; la clave pública de releases permanece en `COMMERCE_RELEASE_PUBLIC_KEY`. El código humano de aprobación no se envía al runner.

Inputs de dispatch: `installer_run_id`, `installer_source_sha`, `expected_job_id`, `expected_device_id`. El origen se fija en `https://commerce-os.inovaris.online`. La preparación debe completarse antes de crear el pairing para aprovechar su TTL. El job Windows tarda como máximo 55 minutos y el helper permite 42 minutos de ejecución. Para el benchmark paralelo, el operador asigna otro job y proyecto nuevos al Mac; el cap del workspace sigue siendo dos renders simultáneos.

El helper importa el worker instalado después de verificar sus bytes, configura carpetas nuevas y privadas y consume el pairing sin imprimir el token. Por autorización explícita, sólo este dispositivo efímero de CI configura `requireAc=false`: el runner puede no exponer alimentación y conserva `ac:null` cuando la lectura es desconocida. El receipt identifica esa política; no inventa una lectura AC. El valor por defecto para equipos de personas sigue siendo `requireAc=true`. Arranca su Node incluido con el daemon real. Al observar el intento esperado, pausa nuevas admisiones y conserva el daemon activo para recuperar el mismo journal ante una desconexión o ACK perdido. Verifica que el attempt y fence no cambien. Sólo al terminar o entrar en cleanup envía STOP y cierra stdin. Lee el journal durable; cualquier identidad inesperada, timeout o fallo provoca un fail con el fence actual cuando es posible y el cierre del único árbol de procesos que creó. La API determina si ese fence sigue vigente. No cambia otros procesos del equipo ni usa shells recibidas de la API.

Al completarse, reconstruye el body original y repite únicamente su misma clave idempotente de `complete`: confirma `REVIEW` y revisión editorial `PENDING`, además de cinco outputs y los doce checks de QA. Esto cubre API → R2 inputs → claim/heartbeat → render instalado → R2 outputs verificados → complete. La emisión del receipt PASS requiere esa confirmación del servidor. El journal completo, inputs, tokens y URLs de acceso quedan fuera del artefacto. Sólo se conserva un JSON con IDs, SHA, tamaños, fases, duración, presión y estado.

Al finalizar, el helper pausa admisión, cierra su proceso y elimina el token/pairing locales. El operador revoca el dispositivo efímero y elimina ambos secrets de GitHub; esa revocación no se delega al token de dispositivo. La revisión editorial y cualquier aprobación de producción permanecen pendientes.

La preparación pasó fixtures de firma, integridad, identidad, QA y redacción, además de TypeScript y ESLint. Esas pruebas sintéticas se distinguen de la ejecución real siguiente.

La captura Windows usa consultas CIM seriales: cuatro intervalos derivados de CPU excedieron el 100%, por lo que el pico instantáneo físico queda **no validado** y los datos brutos se conservan. La revisión editorial y de producción siguió PENDING. [Prueba publicada 2 × 2](evidence/creative-v1/browser-published-2026-09-08T20-03-07-562Z-fc2741ba.json).

Esta evidencia acredita instalación y operación nativa Windows en CI, no en un equipo de persona. Los instaladores internos carecen de certificado de distribución macOS/Windows; la firma Ed25519 de recursos no equivale a Developer ID, notarización o Authenticode.
