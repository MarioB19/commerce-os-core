# Lecturas de salud y presupuesto de diagnóstico · 27-sep-2026

La migración aditiva 0063 crea una proyección tipada de `health_signal`. Antes, cada lectura convertía timestamps JSON y ordenaba todo el historial; el índice textual existente no resolvía ese orden temporal con offsets. Ahora cada cuenta/dimensión selecciona su evidencia más reciente mediante un índice sobre instantes. Se conservan la precedencia determinista, las restricciones del proveedor, la evidencia vencida como antecedente y el rechazo de ventanas inválidas o futuras.

Los registros originales y sus versiones se conservan. El trigger mantiene la proyección dentro de la misma transacción que la evidencia; las cuentas runtime sólo tienen SELECT sobre la nueva tabla. El backfill deriva columnas sin editar los JSON originales ni migraciones aplicadas. Una reversión de aplicación puede ignorar la tabla; no necesita eliminarla ni destruir historia.

Las estadísticas operativas leen siete días de la dimensión relevante y la observación inmediatamente anterior al borde, incluyendo empates. Esto conserva cobertura y reconexiones al inicio de cada ventana. Las tendencias de entrega conservan sus catorce días de efectos. Un intento `NOT_SENT`, liberado antes de contactar al proveedor, no cuenta como envío físico, duplicado o muestra de madurez.

El resumen de Inicio comparte una sola lectura de capacidad y aplica cuatro segundos de presupuesto por sección. Si una fuente falla, devuelve esa sección como no disponible y conserva las demás. El presupuesto comprende adquisición de conexión, locks y consultas, se aplica en PostgreSQL y también en el cliente. Una conexión obtenida tarde se devuelve sin iniciar trabajo; una lectura fallida se destruye para no dejar consultas o transacciones ocupando el pool. Las transacciones son READ ONLY y no dejan timeouts locales en conexiones reutilizadas. `/readyz` del worker usa el mismo mecanismo con dos segundos para la base; sus loops se verifican después de esa consulta.

Estos presupuestos no prometen latencia HTTP máxima ante un event loop bloqueado ni sustituyen la supervisión del servicio. El diagnóstico distingue conexión del proveedor, propiedad de sesión, autorización comercial y progreso del worker. Un heartbeat recién escrito no vuelve sano un loop detenido. La alerta interna de worker indisponible se deduplica y sólo se resuelve con evidencia vigente; su existencia no acredita recepción externa.

El instalador existente detiene API, automatización y canal antes de migrar; la inserción del backfill y `CREATE TRIGGER` necesitan una ventana de publicación. Ingress conserva su recepción durable. Medir el volumen y tiempo productivos, la latencia de salud/capacidad/Inicio y el progreso después de instalar el SHA revisado. El benchmark de [110 mil señales sintéticas](evidence/launch-resilience-20260927/health-performance.json) sólo acredita comportamiento local; no demuestra la causa inicial ni la mejora medida en el VPS.

Pruebas: selección con offsets/valores inválidos, proyección y permisos runtime, cobertura en los bordes, cancelación de SQL lento, pool agotado sin fuga, lectura sin escrituras, contadores NOT_SENT y leases vencidos visibles en Inicio/capacidad/readiness.
