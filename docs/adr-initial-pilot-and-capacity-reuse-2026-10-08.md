# Piloto inicial y reutilización explícita de capacidad

Fecha: 2026-10-08. Estado: implementación y pruebas locales completadas. No acredita provisión, instalación, aislamiento del origen ni vinculación física.

La recuperación conserva las cuentas existentes. El administrador exige que `waha-01` exista y responda; alta crea una cuenta nueva, adopción legacy sólo registra su plaza y expansión preserva las plazas legacy. Por ello se necesita una provisión explícita de la misma cuenta y una preparación técnica acotada del primer gateway. No se reemplazan cuentas para resolver esa dependencia.

`provision_existing` recibe plaza, versión de plaza, cuenta y sesión actuales. Bajo locks canónicos crea únicamente una operación PROVISION para ese mismo binding. Exige REAL congelado, intención de sesión detenida/pausada, ownership congelado sin lease vigente y ausencia de comandos/efectos inciertos o en vuelo. No modifica cuenta, sesión, historial, perfil o permisos. La operación se completa mediante el administrador después de HTTP autenticado y cero sesiones. Un perfil existente deshabilitado permanece deshabilitado: provisión física y habilitación para onboarding son pasos distintos.

La herramienta de piloto acepta una aprobación Root privada ligada al paquete instalado, adopción/plan B02 actuales, backup previo y captura real. Sólo admite slot 1, imagen fijada y compose canónico, credenciales existentes, volúmenes preservados o creación inicial vacía expresamente aprobada, límites y redes explícitos. Primero crea exactamente ese container detenido. Un segundo paso explícito arranca sólo ese servidor y verifica HTTP con la clave existente por stdin, nunca crea/inicia una sesión. No produce aprobaciones Root, aislamiento de fuente, ni adopción automática. Cualquier resultado incierto se conserva para lectura; no hay replay de mutaciones. Después se usa PROVISION y reconciliación CAS Root/B02, seguidos por nuevo backup y restore.

Retirar una cuenta continúa conservando su historia y no libera capacidad. `drain` tampoco la libera. La acción adicional `release` exige la plaza DRAINING, una operación DRAIN terminal comprobada, cero sesiones de lectura fresca, cuenta retirada, sesión detenida, ownership congelado y ausencia de trabajo pendiente/incierto. Sólo entonces pone account_id=NULL y estado PREPARED; conserva gateway, volúmenes, credenciales, cuenta, sesión y operaciones históricas. En SIMULATION se usa únicamente el adaptador sin red y su reloj canónico.

`number_capacity_slots.operation_id` conserva la operación física PROVISION/EXPAND ya SUCCEEDED/VERIFIED cuando otra cuenta reserva esa plaza. El PROVISION de la cuenta nueva se liga por input.slot_id y account_id; las detecciones de trabajo pendiente incluyen ese binding. Así el recibo de infraestructura Root sigue apuntando a su provisión histórica, incluso tras retirar/reutilizar. No se introduce una migración ni se reescribe historia física. La operación de un primer slot aún no verificado sí puede reemplazarse al reconciliar su provisión explícita; no se puede sustituir una operación incierta o activa.

Pruebas requeridas: contrato/API/MCP, revisiones viejas y replay, scope entre tenants, perfiles deshabilitados intactos, rechazo de sesiones/efectos/leases, DRAIN sin liberar implícitamente, release/reutilización con historia y operación física conservadas, y fixtures Root que rechacen desvíos antes de Docker. La prueba Linux con imagen real y HTTP autenticado sigue siendo obligatoria antes de acreditar capacidad productiva; Docker simulado no la sustituye. Los teléfonos permanecen diferidos: revocación auténtica del origen, QR, identidad y recepción física quedan separados.


## Secuencia operativa y sellos

1. Con ocho servicios ya adoptados, crear B02 fresco y custodiado. Root captura runtime antes de crear la operación, con `finished_backup <= captured_runtime <= created_PROVISION`. Adoptar la plaza legacy si aún falta y solicitar `provision_existing` por API con hold liberado y REAL congelado. Conservar versiones y recibos reales.
2. Tomar hold canónico y capturar ownerships. La aprobación Root cerrada de `initial-pilot-root.py` liga SHA/release instalado, hashes previos de adopción/plan, PROVISION, snapshot de volúmenes existentes, runtime previo, tres refs de credenciales, piloto/release env nuevos, compose renderizado y herramientas/backup B02. El archivo de aprobación viene del controlador Root tras revisión real; la herramienta no lo fabrica. La imagen fijada debe estar presente. PRESERVE_EXISTING conserva los dos volúmenes observados; CREATE_EMPTY exige ambos nombres ausentes en inventario nativo aprobado, crea sólo esos dos volúmenes y comprueba ownership Compose y directorios vacíos antes del arranque. La presencia de sólo uno bloquea. Ninguno de esos modos restaura COMOSW01 ni demuestra continuidad de sesión.
3. `prepare REF` crea sólo `waha-01` detenido y añade exactamente las redes de ingress/channel-worker. Guarda intent y prepared privados. `start REF` arranca una vez el CID observado y exige HTTP autenticado sin ninguna sesión. `readback REF` no repite Docker ni guarda una aprobación. Un fallo parcial conserva los journals y exige conciliación; no se borra ni recrea por comodidad. Puerto público, autoarranque, sustitución de volumen/CID/perfil, cambio de otro contenedor y miembro de red ajeno bloquean. El estado detenido se informa sin afirmar cero sesiones.
4. Liberar sólo hold para que el administrador API pueda claim/complete de ese PROVISION; REAL y perfiles permanecen congelados/deshabilitados. Crear de nuevo el hold canónico y su observación auténtica antes de `reconcile-copy-runtime-gateways`; no reutilizar un hold_at anterior. Reconciliar la pareja Root/B02, realizar backup/restore nuevos y sólo entonces liberar el hold transitorio conforme al contrato existente.

El resultado técnico no prueba que las credenciales copiadas sigan autenticando WhatsApp. Si HTTP lista una sesión preservada, incluso detenida, se informa la dependencia de aislamiento/revisión; no se elimina el volumen ni la sesión para obtener un cero ficticio. La red se inspecciona con endpoints reales: un contenedor creado/detenido no tiene endpoint activo y no se inventa su pertenencia viva.


## Continuidad de recibos físicos

Preparar o ampliar también conserva el operation_id físico VERIFIED (EXPAND exige apply=true y sessions_started=0). Los jobs nuevos guardan input.slot_ids explícitos para claim, detección de pendientes y reconciliación. El readback de la plaza conserva overlay_sha del recibo físico histórico aunque el administrador opere con un overlay ampliado distinto; el resultado del job nuevo conserva su propio digest. No se repunta el recibo Root de un container intacto.

Docker CREATED puede devolver NetworkID vacío antes del primer start. El ejecutor valida los ocho servicios existentes con el controlador original y el nuevo container mediante un contrato CREATED separado: deja ese valor vacío en su recibo, obtiene la definición real de docker network inspect y exige cero endpoints de ese container detenido. Después de start exige el NetworkID real de esa misma red. Nunca rellena un CID, NetworkID o endpoint sintético en evidencia productiva.

La prueba opt-in `tests/ci/test_initial_pilot_docker_linux.py` ejecutó los guards reales con Docker 29.5.2 y Compose 5.1.4 en Linux aislado. Ocho procesos Alpine sintéticos y un gateway sintético probaron CREATED→START, rutas reales, identidad, endpoints, dos volúmenes propios vacíos y rechazo de endpoint ajeno/contenido. Limpió únicamente sus recursos etiquetados y conservó el inventario previo de volúmenes. No ejecutó WAHA, HTTP proveedor ni credenciales; esa evidencia valida semántica Docker, no capacidad WhatsApp. El recibo y hashes quedan en `docs/evidence/initial-pilot-linux-docker-20261008.json`.

La prueba detectó tres diferencias que se corrigieron: Compose puede renderizar mem_limit como cadena decimal exacta; `compose create` admite `--no-build --no-recreate --pull never`, y su definición debe carecer de dependencias/build/links/volumes_from; Docker puede normalizar OomKillDisable de false a null al primer start. La identidad normaliza sólo ese default equivalente y rechaza true. El resto de la definición permanece exacto.
